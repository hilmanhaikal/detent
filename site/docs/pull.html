How it pulls

  • It follows the hand at first, then gets heavier, and never passes max. With the defaults it arms 64 px down, after about 89 px of hand.
  • At the line it arms: onArm(true), data-armed on the element, and a tick with haptics. Back above the line, it disarms.
  • Let go while armed and onPull fires once. It holds at rest, with data-busy and aria-busy="true", until you call done(). Pulls while busy are ignored.
  • Let go short of the line and it springs back, with no bounce.
  • On a scroll container it pulls only when the container is at its top, and only downward. Anything else is the native scroll, left alone.
  • A finger and a mouse can pull. A pen pulls where the browser sends touch events for it, as on an iPad; elsewhere it scrolls natively.
  • With reduced motion it jumps to rest or back, with the same result.

On a phone, a pull on the whole page can start the browser's own refresh. Pull an inner list, or set overscroll-behavior-y: contain on the page.

Keys and screen readers

A pull is never the only way. Add a button that calls trigger(), as the demo does: it goes to rest and fires onPull, just like a pull.

While it is busy the element has aria-busy="true", so screen readers wait for the new content. Say the result in your own polite live region, such as "Two new orders." destroy() puts every attribute back.

haptics: true ticks once when the pull arms. It works on Android, not on iPhone, because Safari has no vibration API. Use it for the clicks that matter, not every step.
